# Playbooks

Splunk SOAR playbook templates (`.py` + `.json` pairs) for the `jamf-splunk-soar`
connector. SOAR keeps these in sync via source control (Administration → Source
Control), or a customer imports a `.tgz` export. See the repo root `README.md`
and `CONTRIBUTING.md` for the workflow and the non-negotiable safety rules.

> **Authoring note.** These pairs are normally generated by the Visual Playbook
> Editor (VPE). When a template is hand-authored, the `.py` is the reviewable
> source of truth; the `.json` is a best-effort VPE graph that should be opened
> and re-saved in the editor to canonicalize its layout, ports, and hash.
>
> **Filename convention.** The playbook *name* follows `Jamf - <Scenario>` (Title Case
> + dash, per issue #8), but the on-disk *filenames* are `snake_case`
> (`jamf_compliance_drift_remediation.{py,json}`) on purpose: the `/` in a
> `Jamf - <Scenario>` name makes SOAR treat it as a subdirectory path on export, so the
> file pair is stored snake_cased to keep it a flat, portable pair. The display name
> inside SOAR still reads `Jamf - <Scenario>`.

### `jamf_compliance_drift_remediation`
Apple/MDM-unique template (no shipped SOAR equivalent). Leads with **non-destructive
correction** — redeploy the management framework and send a blank push to force an MDM
check-in — then **checks compliance**. Only if the read *succeeds and* the device is
*still* non-compliant does it contain (quarantine group + lock); a wipe happens **only**
behind an analyst approval prompt whose text states the action is irreversible. Escalation
requires a *present, successful, non-compliant* signal: a failed/403 read (`status != success`)
**or** a successful-but-empty read (`summary.total == 0`) both end the run safely rather than
escalating.

Flow (block names, in order): `resolve_device` → `redeploy_framework` → `force_checkin`
→ `check_compliance` → `is_compliant?` → `quarantine_device` → `lock_device` →
`approve_wipe` → `is_wipe_approved?` → `wipe_device`.

> **Deferred — enrichment stage.** Issue #4 also calls for an enrichment step
> (`get configuration profiles`, `get extension attributes`) alongside the correction
> steps. It's intentionally left out here: the reusable enrichment engine ships in the
> Device Enrichment Input playbook (PR #9). Once #9 merges, wire that Input sub-playbook
> in rather than re-implementing the lookups. The `update inventory` correction step is
> permanently dropped — the connector rejects it for computers (macOS recon is policy-based).

**Customer-config points** (replace the `<...>` placeholders on import):
- Jamf asset — `assets=["<your-jamf-asset>"]` on every action block
- Quarantine static group — `group_name` on `quarantine_device`
- Lock/wipe PIN — `<your-6-digit-pin>` on `lock_device` and `wipe_device`
- Lock return message + callback number — on `lock_device`
- Approver role — on `approve_wipe` (default `Administrator`)

**Datapaths (verified against the live connector "Jamf Pro" v1.0.0):** the resolver
returns the device id at `action_result.data.*.id` and type at `action_result.data.*.type`;
`get compliance status` returns `action_result.data.*.compliance_state` (a string).
Confirm the exact `compliance_state` value ("COMPLIANT") against a real device response.
**Known bug (PR #10 review C1):** the wipe `confirm` param is wired wrong. The connector
requires `confirm` to *exactly equal the `device_id` string*; the template currently sends a
truthy flag (`"true"` in the `.json`, boolean `True` in the `.py`), so an approved wipe is
rejected (`WIPE_NOT_CONFIRMED`) and never fires. Fix pending a VPE edit: wire `confirm` to
`resolve_device:action_result.data.*.id` (as the FileVault playbook does).

### Prerequisites — Jamf API role privileges (set these BEFORE running)

Each action needs specific privileges on the OAuth API role used by the Jamf asset
(Jamf Pro → **Settings → API Roles and Clients**). Missing privileges surface as
**HTTP 403 `INVALID_PRIVILEGE`** at runtime — grant these up front so adopters don't
hit surprise failures. Verified live against the connector 2026-07-01.

| Action in this playbook | Required API-role privilege(s) |
|-------------------------|--------------------------------|
| `get compliance status` | Conditional-access / device-compliance **read** (tenant must have conditional access configured) |
| `redeploy management framework` | **Send Computer Remote Command to Install Package** + **Read Check-In** (the Check-In read is required and easy to miss — it's the usual cause of the 403) |
| `send blank push` | **Send MDM command information in Jamf Pro API** (queued via `/api/v2/mdm/commands`) |
| `lock device` | **Send MDM command information in Jamf Pro API** (queued via `/api/v2/mdm/commands`) |
| `add to static group` | **Update Static Computer Groups** |
| `wipe device` | **Send MDM command information in Jamf Pro API** (queued via `/api/v2/mdm/commands`) |

> The lock / wipe / blank-push commands all queue through the connector's shared
> `/api/v2/mdm/commands` engine (`jamf_connector.py`), so they need the **v2** "Send MDM command
> information in Jamf Pro API" privilege — **not** the Classic per-command privileges. `redeploy
> management framework` is the exception: it uses the Classic remote-command path above.

**Required config values (not privileges) — replace before running:**
- `lock device` needs a real **6-digit `pin`** (the code to unlock the Mac afterward); the
  `<your-6-digit-pin>` placeholder fails connector validation.
- `add to static group` needs a real `group_name` (an existing static group).
- `send blank push` / `get compliance status` etc. take the resolver's `device_id` (`data.*.id`).

> **Note:** `lock device` and `wipe device` are **queued MDM commands** and, on a real
> device, actually lock/erase it. Test against a spare/test device — never a production Mac.

**Safety:** the `approve_wipe → is_wipe_approved` gate must never be removed. The wipe
is reached only on an explicit `Yes` response; a timeout, `No`, or no response never wipes.
